# Перенос @SerbiaJobsBot в Telegram Serverless

Рабочий бот перенесён с Render/Supabase на JavaScript-обработчики и SQLite Telegram Serverless. Python-сборщик **12 активных источников** запускается GitHub Actions примерно каждые 30 минут. Расписание GitHub может задерживаться; уведомления отправляются после обнаружения вакансии при обработке очередного источника. Постоянно работающий Render после переключения не требуется. Политика источников описана в [SOURCE_NOTES.md](../SOURCE_NOTES.md); операция `sources` повторно проверяет отключённые сайты без записи и рассылки.

## Что переносится

### Рекламные рассылки

Владелец открывает `/admin` → «Реклама» → «Создать пост», отправляет текст
или одно фото с подписью (можно переслать готовый пост). Затем показывается
предпросмотр; необязательная кнопка добавляется сообщением
`Текст кнопки | https://example.com`. Отправка требует отдельного подтверждения
с числом получателей. Альбомы и видео пока не поддерживаются.

Получатели фиксируются при запуске: все известные пользователи, кроме отказавшихся
от рекламы и известных заблокировавших бота. Уведомления о вакансиях независимы.
Каждый рекламный пост содержит пометку «Реклама» и только добавленную владельцем
URL-кнопку, если она задана. Пользовательских кнопок управления рекламой нет.
Прежние сохранённые отказы учитываются перед отправкой. Удаление данных и повторная регистрация не возвращают
пользователя в старую очередь.

Первая порция отправляется после подтверждения, следующие — через операцию
Actions `ads`, запланированную между сборами примерно каждые 5 минут. GitHub может
задерживать запуск. Worker работает до 3 минут, по 5 получателей за вызов,
с паузами и обработкой 429. Прогресс и остановка доступны в «Рекламе».
Остановка касается оставшейся очереди, уже отправленные сообщения не удаляются.
При неоднозначном результате отправки запись отмечается неподтверждённой и
не отправляется автоматически повторно. Отдельные фото/текст и рассылки
проверяются тестами без отправки сообщений реальным пользователям.

### Основной функционал

- Меню, поиск, все фильтры, несколько выбранных городов/языков/форматов/периодов, фильтр ВНЖ, ключевые слова, исключения и месячная зарплата.
- Карточки с навигацией, подробностями, переводом, кликабельным адресом Google Maps, исходной ссылкой и контактами.
- Скрытые вакансии и восстановление, помощь владельца, удаление личных данных.
- Мгновенные уведомления после обнаружения; включение пропускает старый каталог. История защищает от повторов. Неоднозначный результат отправки не повторяется автоматически и учитывается в `counts.uncertain`.
- Старые номера вакансий, настройки пользователей, даты, история отправок, прежние избранные записи и диагностика источников. Старые кнопки карточек продолжают работать. Выбор источников в меню отсутствует.

Извлечение языков, требований ВНЖ, адресов и дат остаётся в проверенном Python-коде. В Serverless передаются исходные поля плюс `_cloud` с вычисленными фактами. JSON-настройки и неизвестные старые поля сохраняются.

## Текущее состояние

Переключение завершено: `active=true`, webhook `cloud.telegram.org`, `in_sync=true`, обрабатываются `message` и `callback_query`. Перенесены 15 пользователей, 1 072 исходные вакансии и 22 записи истории. После переключения сборщик уже добавил новые вакансии. Старый Render приостановлен, workflow **Check Serbia jobs** отключён. Не запускайте `stage`/`cutover` повторно: текущая база уже содержит новые пользовательские изменения.

Инструкция ниже сохраняет порядок первоначального переноса. Для проверки работающего бота используйте `check`, для обновления кода — `deploy`, для сбора — `collect`, для паузы и возобновления — `pause`/`resume`.

## Повторные вакансии и обновление кода

Поиск, скрытые вакансии, подсказки фильтров и уведомления используют общий каталог без дублей. Объединяются варианты одной ссылки (`www`, HTTP/HTTPS, метки рекламы), публикации с общей ссылкой на конкретную вакансию и длинные одинаковые тексты с совпадающей должностью и подтверждающими реквизитами. Противоречащие работодатели, адреса, города или зарплаты препятствуют объединению разных ссылок. Одного названия должности недостаточно. Для совпадения только по тексту требуется близость дат до 45 дней. Неполные сведения не должны соединять две противоречащие вакансии.

Под фильтры выбирается подходящая исходная публикация; сведения разных объявлений не смешиваются. Для вариантов одной и той же ссылки сначала выбирается последняя сохранённая версия, чтобы старые зарплата или срок не обходили фильтры. Скрытие любой копии скрывает группу; восстановление снимает скрытие со всех известных копий. Отправка любой копии, включая неопределённый результат, блокирует повторное уведомление. Репост вакансии из каталога до включения уведомлений также не рассылается.

Все исходные строки, ID, контакты и история остаются в SQLite. Это объединение в пользовательских сценариях, без удаления данных. Сильно переписанные объявления без общей ссылки могут остаться отдельными: неоднозначные совпадения не склеиваются.

`deploy` обновляет только код активированного бота, не запускает импорт и не переключает webhook. Перед публикацией сверяется SHA-256 проверенной предыдущей версии из `deploy.py`, выполняется read-only `audit` реального каталога. Официальные `fetch`/`push` проверяют ревизию; после публикации сверяются все модули и маршрутизация. Неожиданные изменения останавливают обновление. При подготовке следующего релиза нужно проверить прежний опубликованный код и обновить `PREVIOUS_DIGEST`. Повторный запуск того же релиза ничего не перезаписывает.

## Перед первоначальным переключением

В GitHub → Settings → Secrets and variables → Actions:

- `TGCLOUD_PROBE_TOKEN`: уже существующий CLI-токен основного бота.
- `SUPABASE_SERVICE_ROLE_KEY`: серверный ключ Supabase. Его можно скопировать в Supabase → Project Settings → API Keys → Legacy API Keys → service_role. Новый серверный `sb_secret_…` также поддерживается. Публичный anon/publishable ключ не подходит.

`SUPABASE_URL` задан в workflow: `https://iajwyuldjwptkbafpmgl.supabase.co`.

Секреты не включаются в код, ZIP или отчёты. Программа читает приватные данные в память, передаёт их через stdin дочернему процессу, не печатает строки пользователей и не загружает снимок базы как Actions artifact. Supabase остаётся неизменной резервной копией на момент перехода.

## Порядок действий

После публикации этого кода в main откройте Actions → **Serbia Jobs Serverless** → Run workflow:

1. `check` — проверить выполнение кода в Telegram и состояние базы. Публикации обработчиков нет.
2. `stage` — пробное копирование всех пяти таблиц. Скрипт читает базу обратно и сравнивает все поля, затем проверяет неизменность webhook. Старый бот продолжает работать. Запуск можно повторять до первого включения новой версии.
3. Для окончательного перехода **приостановите сервис Render** `serbia-jobs-bot` и отключите старый workflow **Check Serbia jobs**. Дождитесь завершения уже запущенного старого сборщика. Это необходимо: иначе старый процесс может продолжить рассылку или вернуть себе webhook.
4. Запустите `cutover`, отметив `legacy_stopped`. Скрипт ещё раз копирует актуальные данные, сверяет их и повторно читает Supabase, чтобы обнаружить записи, изменившиеся во время переноса. Затем публикует обработчики, проверяет их содержимое, переключает webhook **без удаления ожидающих обновлений**, включает обработку и отправляет владельцу проверочное меню. После этого выполняется первый сбор.
5. Проверьте `/start`, фильтры, поиск и скрытые вакансии в @SerbiaJobsBot. Результат `check` должен показывать `active=true` и `webhook_in_sync=true`. Просмотрите результат `collect` и диагностику источников. До этих проверок не удаляйте старую Supabase.

`preview` отправляет только владельцу меню для проверки оформления. Его получение само по себе **не подтверждает переключение**: кнопки обслуживает текущий webhook. `pause` останавливает обработку/рассылку новой версии, не стирая данные и не возвращая прежний webhook. `resume` с отметкой `legacy_stopped` возобновляет уже активированную версию без повторного импорта; webhook должен по-прежнему указывать на Serverless.

Новый scheduled workflow до активации завершает работу без сбора и рассылки. Платформа Serverless не запускает произвольный Python или постоянно работающий polling; сбор вынесен в GitHub Actions. Доступность источников, лимиты Serverless beta и GitHub Actions определяют фактическую частоту работы.

## Сбой и восстановление

До активации старые данные не изменяются. Если импорт/сверка не прошли — исправьте доступ или причину и повторите `stage`/`cutover`. Если предыдущий запуск уже опубликовал точно эту же версию, повторный `cutover` разрешён до первой активации; чужие или изменённые удалённые модули автоматически не перезаписываются.

Если переключение остановилось до активации, можно возобновить Render: при старте Python-бот вновь зарегистрирует свой webhook с прежними секретами. После успешной активации повторный импорт поверх базы **запрещён**, даже если новая версия приостановлена. После появления новых пользовательских изменений простой возврат к старой Supabase потерял бы их — сначала нужен обратный перенос. Такой откат автоматически не выполняется.

База использует изолированные таблицы `sjc_*`; таблицы прежней пробы `sj_probe_*` не затрагиваются. `init` создаёт таблицы через поддерживаемый SDK raw SQL. `schema.js` намеренно отсутствует: публикация обработчиков не запускает отдельную разрушительную миграцию схемы.

Endpoint `admin` доступен только при owner CLI run, отклоняет контекст Mini App и Telegram update. Любой пользовательский ввод обрабатывается только личными `message`/`callback_query`; SQL использует связанные параметры. Обработчики и рассылка используют одну аренду на пользователя. При 429 от Bot API сохраняется общая пауза; 403 выключает подписку; неоднозначная отправка не повторяется. Отдельно обрабатывается HTTP 429 от управляющего API Telegram Cloud: внешний worker ждёт указанную паузу и делает до трёх повторов. Таймауты, 5xx и ошибки внутри уже запущенной функции автоматически не повторяются, поскольку запись или отправка могла выполниться.

## Карточки, качество и диагностика

В карточке остаются ссылка на объявление, подробности, «Ещё» и перелистывание.
Перевод, скрытие, жалоба и возврат к фильтрам находятся в «Ещё»; возврат сохраняет позицию.
Требования к опыту и помощь с документами выводятся только при явном указании работодателя.
Проверка качества исключает явные резюме, услуги, рекламу, подборки и закрытый набор.
Закрытие исходного Telegram-поста снимает также распознанные копии вакансии.

Жалоба скрывает группу только для отправителя. Владелец (`/admin`, кнопка в его меню)
может снять её с общей выдачи или оставить, а затем вернуть снятое объявление.
Раздел проверяет владельца по числовому ID, в том числе при поддельных callback.
Отчёт показывает сбор, источники, повторы, жалобы и проблемы доставки; время — Белград.
Обновление `deploy` также запускает `refresh_facts.py`: только вычисляемые признаки,
без замены исходных полей, ID, пользователей и истории уведомлений.

Перевод использует Google, при недоступности — MyMemory для распознанного сербского,
английского текста. Русский текст при отказе основного сервиса остаётся исходным.
Отправляется только публичный текст вакансии. Результат хранится 30 дней и проверяется
на совпадение с исходным текстом. HTTP 429 и исчерпание квоты включают паузу; ошибки
не сохраняются как перевод. Бесплатные сервисы не гарантируют доступность: при отказе
обоих остаётся оригинал и ссылка на перевод в браузере.

## Локальная проверка

```sh
cd serverless
npm ci --ignore-scripts --no-audit --no-fund
npm test
cd ..
python3 -m unittest discover -s tests -q
```

Node 24, Python 3.12. Runtime-модули `tgcloud/` не импортируют Node/npm: только `sdk` и локальные JS-файлы. `bridge.mjs` работает снаружи платформы, использует клиент закреплённого официального `@tgcloud/cli@0.2.0` и не публикует ничего при `run`. Публикация выполняется официальными `fetch`/`push` с проверкой ревизии, без `--force`.

Для команд `python3 serverless/migrate.py check|stage|cutover|preview|pause|resume` и `python3 serverless/collect.py` нужны соответствующие переменные окружения. В управляемой среде с сетевым прокси Node запускается с `NODE_USE_ENV_PROXY=1`; CA-настройки среды сохраняются.
