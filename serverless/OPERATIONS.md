# Эксплуатация @SerbiaJobsBot

## Резервные копии и восстановление

Workflow **Encrypted SQLite backup** запускается ежедневно в 03:43 UTC и после
успешной автоматической публикации. Расписание GitHub может задерживаться.
Он создаёт согласованный снимок одним SQL INSERT…SELECT с UNION ALL: все ветви
читают одно состояние SQLite. Сохраняются пользователи, вакансии с ID и исходными
ключами, история доставки, все прикладные записи (модерация, жалобы, реклама,
переводы, лимиты, статистика), метаданные, дедупликация updates и счётчик ID.
Текущие leases и таблица временных снимков в копию не входят.

Из снимка собирается настоящая SQLite. Она проверяется через integrity_check,
сжимается и шифруется **AES-256-GCM** стандартной криптографией Node. Ключ HKDF-SHA256
выводится из существующего `TGCLOUD_PROBE_TOKEN`; для каждого файла случайны соль
и nonce. Заголовок также аутентифицируется. Значение секрета не меняется и не
печатается. Новый секрет и платная инфраструктура не нужны.

Публичный Actions artifact содержит только `runtime.sjcbk` (шифротекст) и отчёт
с общими счётчиками/контрольной суммой. Открытая SQLite, Telegram ID и тексты
запросов в artifact не попадают. Хранение — **7 дней**; старые копии автоматически
истекают. Удалённые из текущей базы данные могут оставаться в исторических
зашифрованных копиях до истечения этого срока. Временный снимок в облачной БД
удаляется после экспорта, а оставшийся после сбоя — при следующем снимке через
24 часа. Не загружайте расшифрованный файл в публичный репозиторий или artifact.

Каждая копия проходит расшифровку, integrity_check и полное сравнение всех полей
с исходным снимком. Проверяется повторное чтение файла с диска и работа кода бота
на восстановленной SQLite в отдельном временном каталоге. Smoke test использует
локальный Telegram-заглушку, не получает Cloud-секрет и не выполняет сетевые
отправки. Production-база не восстанавливается и не останавливается при проверке.
После успешной загрузки artifact отмечается время копии в админке. Независимый
watchdog предупреждает, если более 36 часов нет подтверждённой копии, и сообщает
о восстановлении без повторных одинаковых предупреждений.

Для локальной проверки скачанного artifact используйте Node 24 и Python 3.12.
Существующий Cloud-токен передайте через защищённое окружение `TGCLOUD_TOKEN`,
не через аргументы и не в чат:

```sh
python3 serverless/backup.py verify /path/to/runtime.sjcbk
python3 serverless/backup.py restore-local /path/to/runtime.sjcbk --output /new/private/restored.sqlite
```

Путь назначения должен быть новым. Восстановленная локальная база всегда
`active=false`; исторические рекламные кампании блокируются аварийной отметкой.
Неопределённые отправки и обработанные updates сохраняются, чтобы избежать
повторов. Это инструмент локального восстановления и проверки, он не перезаписывает
рабочую Cloud-базу. Перенос восстановленных данных в рабочую платформу требует
отдельной аварийной процедуры с проверкой целевой базы и маршрутизации.

Для расшифровки требуется именно тот Cloud-токен, которым создан файл. При будущей
согласованной ротации нужно заранее расшифровать/перешифровать сохраняемые копии
или сохранить старый ключ в безопасном хранилище. В этой задаче ротации нет.

## Actions: фактические затраты и оптимизация

На 18 октября 2026 проверены timing API шести последних плановых запусков
серверного workflow: `39115145824`, `39113786507`, `39098949463`, `39096792971`,
`39082889459`, `39081073352`. Длительности: **23, 89, 18, 79, 17, 83 секунды**
(среднее 51,5 с). Для всех GitHub сообщил **billable UBUNTU total_ms=0**.
Это публичный репозиторий со стандартным ubuntu-latest; выбранные запуски не
расходовали платные минуты. Эта проверка не является просмотром всех счетов
аккаунта. Ограничения хранения artifacts/cache всё равно нужно учитывать.

Полные тесты остаются обязательными checks `tests` и `security` для PR/main,
а также запускаются перед ручными операциями и публикацией. Они больше не
повторяются на каждом плановом сборе/рекламном тике. При полном исполнении
расписания это убирает до 288 повторных запусков тестов в сутки. Расписание
сбора и продолжения рекламы сохранено. Добавлен npm-cache в независимый watchdog;
npm ci сохраняет проверку lockfile, install scripts отключены. Supabase-секрет
теперь передаётся только явно выбранным старым операциям stage/cutover, которые
по-прежнему запрещают повторный импорт в активированный бот. Render и старый
workflow не включаются.

## Качество, свежесть и статистика

`/admin` → **Качество базы** показывает число распознанных копий, закрытых /
просроченных публикаций, объявлений старше 30 дней и записей без даты. Возраст
сам по себе не закрывает вакансию. Раздел **Польза источников** показывает
доступные и исключительные для источника группы, внутренние копии, число сбоев
и последовательные неуспешные сборы. История начинает накапливаться после
установки; старая история не выдумывается. Статусы записываются один раз на
источник и collection run, включая повторы collection_end.

**Возможные дубли** — консервативные кандидаты с одинаковой должностью,
работодателем и городом, которые обычное объединение не склеило. Показываются
только доступные вакансии. Решение принимает владелец; новых автоматических
объединений и удаления данных нет. Жалобы на устаревшие записи и повторы остаются
в прежнем разделе модерации.

При поиске показывается предупреждение, если последний успешный сбор старше
двух часов либо ещё не подтверждён. После свежего успешного сбора оно исчезает.
Успех — завершённый сбор хотя бы с одним исправным источником; общий успех не
означает исправность каждого источника (их состояние видно владельцу отдельно).

`/admin` → **Статистика**: активные пользователи за сегодня/7/30 дней, текущие
подписки на вакансии, число новых поисков, доля пустых поисков и запросы перевода
за 7 дней. Даты агрегирования — UTC. Перелистывание и подробности не считаются
новым поиском. Счётчики обновляются атомарно в SQLite, хранятся 90 дней. Для
активности сохраняется только день последнего обращения в существующей записи
пользователя; нет отдельного журнала событий, текстов запросов и значений
фильтров. Удаление данных удаляет и этот день вместе с пользователем; обезличенные
суммарные счётчики остаются. Новые разделы доступны только числовому владельцу
340780041 в его личном чате. Пользовательское меню дополнительными кнопками
не перегружено.

## Пользователи в админке

«Статистика» показывает число текущих профилей, уникальных пользователей,
наблюдавшихся с начала учёта, активных и новых за сегодня / 7 / 30 дней (UTC),
а также включённые уведомления. Поиски и переводы доступны отдельной кнопкой.
Импортированные профили без `last_seen_day` входят в базу, но не в наблюдавшуюся
активность. Регистрации определяются по `created_at`; удалённые профили не
учитываются, повторный вход после удаления создаёт новую регистрацию.

«Блокировки и доставка» считает пользователей, а не ошибки отправки.
Оба worker — рекламы и вакансий — при 403 атомарно отмечают недоступность.
Только явное `bot was blocked by the user` считается подтверждённой блокировкой;
деактивированные аккаунты, прочие 403 и прежние отказы без причины различаются.
Сырые сообщения Telegram не сохраняются. Хранятся состояние, день UTC и флаг
«когда-либо подтверждённо блокировал» в существующем профиле; удаление профиля
удаляет и эти данные. Реальное входящее взаимодействие снимает текущий отказ,
не включая уведомления заново. Повторные ответы и перезапуски не увеличивают
число пользователей. Полный список блокировок Telegram не предоставляет;
проверочных рассылок нет, поэтому это наблюдаемые данные, а не мгновенный охват.
Все страницы требуют числовой ID владельца и его личный чат.

## Баны команды

`/admin` → «Баны»: добавить числовой Telegram ID, проверить ID в предпросмотре
и подтвердить бан. Разбанить можно кнопкой у ID в списке. Владелец не может
забанить себя. Все страницы, callback-действия и ввод ID проверяют числовой ID,
личный чат и актуальную роль исполнителя. Полномочия описаны ниже.

Бан (`user_ban` в `sjc_records`) действует до снятия уполномоченным администратором или владельцем, в том числе до
первого обращения пользователя и после удаления/пересоздания его профиля.
Записываются ID, время, причина, сведения об администраторе и квитанция
одноразового уведомления; этот список входит в существующий зашифрованный
backup. После одноразового уведомления бот молча игнорирует сообщения, команды
и callback-запросы забаненного: даже callback acknowledgement не отправляется. Проверка выполняется
до регистрации/учёта активности и повторно под пользовательским lease.

Обе очереди проверяют бан под тем же lease; рекламный snapshot исключает уже
забаненных, а существующая очередь пропускает забаненных после её создания.
Бан получает lease целевого пользователя: если доставка/обработка уже идёт,
владелец видит кнопку повтора, а подтверждение успешного бана выдаётся только
после сохранения запрета. Настройки подписки не меняются; разбан восстанавливает
обычную обработку, а уведомления продолжают действовать по сохранённым настройкам.
Баны команды и блокировки бота пользователями показаны в статистике отдельно.

## Одноразовые картинки о блокировке и разблокировке

Новый бан: ID → обязательная причина (до 300 символов) → подтверждение.
Картинка содержит причину и фактического администратора, подтвердившего действие:
числовой ID, имя и при наличии username берутся из проверенного Telegram update,
а не из пользовательского текста. При разбане сохраняются автор прежнего бана
и администратор, снявший его. Ссылка обращения всегда ведёт на @AngryVirus,
как в «Помощи». Права управления проверяются по текущей роли в личном чате; роли описаны ниже. Старые баны без причины и имени остаются действующими;
они не получают массового уведомления задним числом.

Текст и кнопка связи показываются одной PNG-картинкой без подписи и URL-кнопкой.
Состояние бана, версия решения и квитанция уведомления записываются атомарно
в одну строку `user_ban`. После разбана строка остаётся с `active:false`, чтобы
повторный callback не отправлял картинку заново; список банов, статистика и
обе очереди считают только активные запреты. Удаление профиля удаляет
неактивную строку, причину, сведения об администраторе и квитанцию.

Уведомление отправляется один раз на каждое изменение статуса. Предварительный
`pending → sending` claim и пользовательский lease защищают параллельные workers.
После таймаута, потери подтверждения или прерывания `sending` автоматического
повтора нет: Telegram не поддерживает ключ идемпотентности sendPhoto, поэтому
абсолютную гарантию ровно одной доставки при сетевом сбое дать нельзя.
Только явный 429 возвращает уведомление в pending с ожиданием retry_after.
Явный 403 ждёт реального следующего обращения пользователя; фон его не повторяет.

Если пользователь ещё не запускал бот, уведомление ждёт первого личного
обращения. Это единственный ответ забаненному; следующие обращения и callback
игнорируются. Новое решение заменяет старое недоставленное уведомление.
Устаревшие подтверждения и кнопки разбана не меняют более новое решение.

До 5 ожидающих служебных уведомлений обрабатываются существующим запуском
`ads_tick`, отдельной функцией и квитанциями внутри записей модерации. Они не
создают рекламных кампаний, не входят в их аудит/прогресс/лимиты и не используют
очередь вакансий. Дополнительного запроса к Telegram Cloud на каждый tick нет.
Проверка operations_check только рендерит обе картинки и ничего не рассылает.

В поле пользователя можно ввести ID или @username. Теги сохраняются только из
проверенных Telegram updates и обновляются при обращении пользователя. При вводе
тега совпадение обязательно проверяется через getChat по известному числовому ID;
перед подтверждением оно проверяется ещё раз. Смена/переиспользование username
не должно приводить к бану прежнего владельца тега. Для старых профилей без тега
проверяется до 30 недавно активных известных боту ID, без отправки сообщений.
Неизвестный или неоднозначный тег требует ввода ID; произвольные личные аккаунты
Telegram Bot API по username не находит. Сам бан всегда привязан к числовому ID.

## Роли и журнал команды

`/admin` → «Команда»: владелец назначает модераторов и администраторов по ID
или проверенному @username с отдельным подтверждением. Администраторы видят
раздел «Модераторы» и могут выдавать/снимать только эту роль. После изменения
прав человеку отправляется одно служебное уведомление, как описано ниже.

| Роль | Доступ в панели |
|---|---|
| Модератор | Бан обычного пользователя с причиной и подтверждением |
| Администратор | Бан/разбан обычных пользователей и модераторов; назначение/снятие модераторов |
| Владелец | Все функции, назначение/снятие администраторов, журнал команды |

Действует защита иерархии: нельзя банить себя, владельца или сотрудника с
равными/более высокими правами. Администратор не может понизить другого
администратора через назначение модератором. Только владелец может менять роль
администратора. Владелец определяется неизменяемым числовым ID 340780041;
его права нельзя снять записью в базе или callback. Сотрудники не получают
доступа к рекламе, статистике, источникам, жалобам, снятию вакансий и журналу.
Модератор не видит список разблокировки и управление командой.

Роли хранятся в `staff_role` внутри существующей SQLite. Они переживают
перезапуск и удаление/пересоздание профиля. Блокировка сотрудника делает доступ
неактивным, пока действует бан. Отзыв роли не снимает автоматически роли,
ранее законно выданные им другим людям.

Каждый защищённый route, callback и шаг ввода заново проверяет числовой ID,
личный чат и роль. Изменения прав используют lease целевого пользователя,
совпадающий с обработкой его входящих действий. Если действие уже выполняется,
для изменения роли нужно повторить запрос; успешное подтверждение выдаётся
только после сохранения. Сохранённые черновики сбрасываются при смене роли;
устаревшие кнопки дополнительно проверяют версию и актуальные полномочия.

«Журнал команды» доступен только владельцу. С новой версии фиксируются баны,
разбаны, назначения и снятия ролей: кто, с какой ролью, над кем, когда, причина
бана и прежняя/новая роль. Время показывается по Белграду. Обычные поиски,
содержимое пользовательских сообщений и клики по меню не журналируются.
Решение и строка `staff_audit` записываются одним атомарным SQL-выражением:
ошибка записи журнала отменяет изменение. Повтор события с той же версией
не создаёт дубликата. Журнал сохраняется после удаления профиля в пределах последних 10 дней и входит в
существующую зашифрованную резервную копию вместе с ролями.


После изменения роли бот отправляет пользователю личное уведомление: назначение
модератором/администратором или снятие соответствующих полномочий. При смене роли
сообщение поясняет повышение или понижение, прежнюю и новую роль, имя/тег и ID
того, кто выполнил действие. Кнопка ведёт в доступную
панель либо главное меню. Отправка заявляется атомарно с решением и аудитом;
повторные подтверждения не отправляют уведомление заново. Сбой Telegram не
отменяет права; инициатор различает ожидающую и неподтверждённую доставку. Только
явный 429 оставляет уведомление ожидающим до retry_after; существующие фоновые
тики повторяют его после паузы. Неоднозначные таймауты не повторяются
автоматически, чтобы исключить дубли.

Обработанные входящие сообщения в личном чате удаляются после сохранения
результата и отметки update как завершённого. Это касается команд, введённых
ID, причин, фильтров и рекламных заготовок: текст и file_id сохраняются до
удаления оригинала. Ошибка удаления не повторяет выполненное действие; при
повторной доставке завершённого update повторяется только попытка удаления.
Незавершённая обработка, сообщения в группах, callback-панели и игнорируемые
сообщения забаненных пользователей не удаляются. Ограничения Telegram могут
помешать удалению; текст входящего сообщения в лог не попадает.
Кнопка связи остаётся в уведомлении забаненному, но убрана из подтверждения
бана в административной панели.


В списке команды выбирается сотрудник и открывается его карточка. Владелец
может напрямую повысить модератора до администратора или понизить администратора
до модератора; промежуточное снятие полномочий не требуется. Снятие и смена роли
требуют отдельного подтверждения с прежней и новой ролью. Администратор видит
карточки только модераторов и может только снимать их полномочия. Каждое
подтверждение заново проверяет роль инициатора, версию решения и lease цели.

Журнал команды хранится 10 суток по времени события. Старые записи физически
удаляются при новых решениях, открытии журнала и независимой плановой проверке
здоровья; последняя выполняет очистку даже при приостановленном боте. Сами роли,
баны и журнал рекламы этой очисткой не затрагиваются. Существующие зашифрованные
снимки базы сохраняются по прежнему сроку резервных копий. Диагностический
operations_check продолжает проверять панели без записи и очистки данных.


## Персональные данные и краткоживущая защита

Профиль содержит Telegram user/chat ID, последний подтверждённый username и день
его наблюдения, фильтры/состояние ввода, дни активности и состояние доставки.
Username берётся из Telegram updates и сверяется через getChat при модерации;
сам по себе тег не даёт прав. Причины банов и записи решений содержат сведения
об исполнителе из подтверждённого update: ID, имя и username, если он имеется.
Это служебные данные модерации, а не журнал всей переписки.

`/delete_me` удаляет профиль, настройки, username, скрытые вакансии, личную
историю доставки, жалобы и кэш меню. Активные баны и записи ролей сохраняются,
включая защитные версии решений, чтобы удалением нельзя было сбросить запрет,
права или повторить старую административную кнопку. Журнал команды остаётся
только в пределах **10 дней**. Неактивная запись бана удаляется вместе с профилем.
Публичные вакансии и общие обезличенные счётчики не удаляются.

Лимиты поиска/навигации — 40 запросов за минуту, перевода — 10 за минуту,
жалоб — 5 за минуту и 20 новых за сутки. Окно отсчитывается от первого запроса.
Счётчики с ID и сроком окончания переживают удаление/повторную регистрацию
**только до окончания исходного окна**, чтобы `/delete_me` не обходил лимит.
Квитанции обработанных updates и минимальные квитанции применения ввода
сохраняются до 48 часов; они не содержат пользовательский текст. При новом
update и плановом обслуживании просроченные записи очищаются индексированными
порциями не более 100 строк каждого типа за проход. Физическая очистка после
длительного простоя может занимать несколько проходов; просроченные окна уже
не ограничивают пользователя.

Кэш меню действует до 7 дней и ограничен 30 записями на пользователя; переводы
публичных вакансий — до 30 дней; агрегаты статистики — 90 дней. Журнал рекламы
отделён от журнала команды и его срока. Временный staging резервного снимка
имеет TTL 24 часа; сохранённые зашифрованные artifacts истекают через 7 дней.
Поэтому удалённые записи могут оставаться в более ранних зашифрованных копиях
до окончания этого срока. Старый Supabase — отдельная историческая копия,
которую нельзя выдавать за актуальную резервную копию.

## Бюджет Cloud API и возобновление

Сбор и рассылка обходят работу ограниченными порциями, сохраняют курсоры и
продолжают незавершённый обход в следующих тиках. Обновление вычисляемых фактов
не читает весь каталог при неизменном хеше кода; при новой версии использует
постраничный курсор и проверяет, что исходная запись не изменилась параллельно.
Это сохраняет корректность свежих данных и уменьшает повторные Cloud-запросы.

Тяжёлые workflows координируются через read-only GitHub Actions API встроенным
`GITHUB_TOKEN`; watchdog имеет приоритет. Применяются паузы между запросами и
ограниченный бюджет повторов явного HTTP 429. Резервный снимок читается
страницами с учётом числа строк и размера ответа, без сетевых отправок при
локальной проверке восстановления. Cleanup после сбоя выполняется по возможности
и не превращает исходную ошибку в ложный успех. Новый секрет и платные сервисы
не требуются. Успех копии подтверждается только завершённым backup workflow,
загруженным artifact и проверкой восстановления, а не одним успешным deploy.

## Исходные архивы и старая инфраструктура

Актуальный исходный ZIP собирается из проверенного коммита:

```sh
python3 tools/build_release.py --output dist/serbia-jobs-bot.zip
```

В main ZIP не хранится. Сборщик включает новые модули разрешённых каталогов,
workers, проверки, инструкции и лицензии; исключает `.env`, базы, private,
node_modules, work, dist и служебные данные платформы. Тест распаковывает релиз
в чистый каталог без Git и проверяет импорт/локальную обработку со заглушкой.

Старый collector перенесён в `deploy/legacy-collect.yml.disabled`, где GitHub
его не исполняет. `render.yaml` и systemd-пример помечены архивными, а CLI
старого Python-бота блокирует polling/webhook без явного opt-in. Render должен
оставаться приостановленным. Shared Python-модули миграции и сбора сохраняются.


## Сохранённые поиски и подборки

Главный пользовательский экран сохраняет прежние пять кнопок. В фильтрах
добавлена одна точка входа «Мои поиски». До трёх записей `saved_searches`
в профиле содержат имя (до 40 символов), снимок разрешённых фильтров, свой
notification baseline и отметку последнего открытия. Служебные настройки,
роли и скрытые вакансии в снимок фильтров не копируются. Скрытые вакансии
общие для пользователя. Загрузка снимка не меняет настройки уведомлений. В «Ещё» можно заменить
снимок текущими фильтрами с отдельным подтверждением: название и флаг
уведомлений сохраняются, граница уведомлений обновляется, старые подборки
этого поиска очищаются. Переименование не меняет снимок и границы.

Каждый сохранённый поиск включается отдельно и начинает уведомлять только
о новых после включения записях. Базовая подписка на текущие фильтры
продолжает работать независимо. Очередь учитывает пользователей с любой
активной подпиской, каталог готовится один раз на пакет. История доставки
остаётся общей по пользователю и вакансии: пересечения поисков не дублируют
сообщения. Бан, удаление профиля, 429, неопределённые отправки и модерация
обрабатываются прежними защитами. При подтверждённом 403 все подписки
пользователя выключаются.

«Новое» — объявления, впервые обнаруженные после прошлого открытия именно
этого поиска. Первый просмотр устанавливает границу, последующие показывают
кнопку только при наличии новых совпадений. Обновление или копия объявления
со старым ID не считаются новыми. Отметка и сессия сохраняются атомарно с
квитанцией действия; старый повтор не откатывает более свежую границу.
Сессии содержат только контекст фильтров, ID и режим просмотра: до шести
записей на пользователя, срок действия 24 часа. Просроченные записи
не используются и вытесняются следующими открытиями.

«Похожие» доступно в «Ещё». Локальные признаки профессии и общие слова
заголовка определяют релевантность, город и языки уточняют порядок.
Ключевые слова исходного поиска снимаются, остальные фильтры сохраняются;
это прямо указано в подборке. Скрытые, закрытые, снятые модерацией записи
и копии исходного объявления не рекомендуются. Навигация, перевод, скрытие,
жалобы и возврат сохраняют контекст подборки.

Подсказки осторожности вычисляются локально по ограниченному публичному
заголовку и описанию: без сетевых запросов, личных сообщений и автоматических
решений о блокировке. Причины ограничены тремя устойчивыми кодами.
Отрицания, обычная зарплата, оплата обучения работодателем и обучающие
предупреждения исключаются по консервативным правилам. Отсутствие подсказки
не означает проверки работодателя. Перевод не изменяет признаки, найденные
в исходном тексте.

# Исправление пограничных случаев фильтрации

Производные факты `_cloud` теперь включают восстановленный `remote` и отдельный
объект `salary` с известностью суммы, нижней/верхней границами, валютой и периодом.
Зарплата «до 500 EUR/месяц» не проходит минимум 1000 EUR как неизвестная;
почасовая сумма остаётся указанной зарплатой, но не становится месячным доходом.
Русский, сербский и английский используют один набор восстановленных фактов.
`refresh_facts.py` пересчитывает прежний каталог с CAS и сохранённой позицией;
в хеш версии включены словарь фильтров и правила зарплаты. Выборы, скрытые записи
и история отправок при этом не сбрасываются.

Суммы проживания, обучения и других расходов не считаются оплатой труда.
Явная структурированная зарплата источника получает публичную отметку
`salary_source=structured`. В старом кэше без этой отметки точное совпадение
суммы, валюты и периода с расходом пересматривается: отдельная явная зарплата
восстанавливается, иначе производная зарплата становится неизвестной до нового
сбора. Обновление фактов сохраняет исходные поля объявления.

Набор пользовательских параметров сохранён. ВНЖ обозначает требование работодателя,
прежний `no_serbian` показывается читаемо без скрытой смены значения. Сессия поиска
проверяет снимок своих условий перед любым действием, включая жалобу и перевод;
чужие фильтры и изменение основного поиска не обесценивают сохранённый поиск.

# Возобновляемый сбор источников

После подтверждённого `collection_end` с исправными источниками сборщик вызывает
существующий `health_tick`: восстановление не ждёт следующего независимого watchdog.
Ошибка этого отдельного запроса не отменяет сохранённый сбор и не выводит детали
шлюза; подавление одинаковых уведомлений остаётся в SQLite. Нулевое число исправных
источников и неподтверждённое завершение восстановлением не считаются.

Для обычных `telegram_`-каналов производный допуск в Сербию повторно проверяется
по тексту вакансии без издательского подвала. Старые `country=RS` и `location=Raca`,
полученные из делового сокращения RACI, сами по себе не подтверждают географию.
Правильные Rača/Rači и явные `u Raci` сохраняются. Пересчёт фактов скрывает прежние
ошибочные допуски; очередной сбор заново читает свежую страницу и исправляет город.

Многочасовые пропуски плановых Actions возможны и при cron каждые пять минут.
Watchdog также зависит от GitHub schedule. Этот выпуск сохраняет двухчасовой
сигнал и не обещает регулярность, которую платформа не гарантирует; независимый
внешний триггер требует отдельного подключения и согласования новых секретов.

Дополнительную возможность даёт `catch-up.yml`: после успешного watchdog на текущем
`main` отдельный workflow проверяет `collection_due` и при необходимости запускает
сбор без рекламы. Независимый watchdog к этому времени уже завершён; резервный
сбор входит в общую очередь `serbia-jobs-collection` с `queue: max` и в координацию
тяжёлых Cloud-заданий. Проверка свежего, приостановленного или уже работающего
сборщика не запускает ещё один сбор. Новые cron, сервисы и секреты не добавляются.

Резервные копии используют ту же очередь GitHub, что публикации и сбор.
Ожидающее задание не занимает runner и не начинает десятиминутное ожидание Cloud
до завершения предыдущего тяжёлого задания. Независимый watchdog сохраняет свою
очередь и может сообщить о сбое, пока служебные задания ожидают. Координация по
метаданным Cloud остаётся страховкой для старых уже запущенных workflow.

`collect.py` получает ограниченное состояние каждого активного источника через
`collection_state` внутри принадлежащего ему collection lease. Публичные курсоры,
очередь URL и SHA-256 недавно проверенных URL хранятся отдельно как `collection_crawl`,
без пользовательских данных и текста вакансий. Состояние ограничено 90 КиБ,
очередь — 48 ссылками, история — 1000 хешами. Адаптер заново проверяет домен,
тип страницы и параметры курсора; запись состояния сама по себе не разрешает запрос.

Вакансии отправляются пакетами до 25 записей и 90 КиБ. После всех подтверждённых
пакетов отдельный пустой `collect` сохраняет статус и checkpoint. Частичная ошибка
не продвигает позицию. Параллельные повторы и старый worker после смены владельца
блокировки не могут продвинуть состояние нового запуска. Известные URL перепроверяются
через сутки; хеши старше недели удаляются. Исчезновение из одного списка не закрывает
вакансию; подтверждённые закрытия и сроки обрабатываются прежним путём.

`scheduled.py` в каждом фоновом тике читает `collection_due`: если успешного сбора
нет 30 минут и действующего collection lease нет, запускает ограниченный обход.
Приостановленный бот не собирает и не отправляет. Реклама сохраняет отдельную очередь
и все подтверждения владельца. После deploy выполняется обычный сбор для проверки
новой версии на настоящих источниках; рекламные кампании для проверки не создаются.
GitHub может задерживать или пропускать тики: точный интервал не гарантирован.

`healthy` описывает доступность. `partial + healthy:true` означает исправный источник
с незавершённым обходом, а не ошибку. Сетевые и ошибки разбора остаются неисправностью.
Число проверенных карточек не означает размер всего каталога. Вся диагностика
показателей обхода доступна владельцу, главное пользовательское меню не расширяется.
### Понятная навигация владельца

В отчёте владельца пять разделов: «Вакансии» (жалобы и снятые объявления),
«Пользователи» (статистика и блокировки), «Команда» (сотрудники и действия
за последние 10 дней), «Сбор вакансий» (источники, проверка базы, подробный
отчёт) и «Реклама». Кнопки расположены по одной в строке. Администратор
и модератор продолжают видеть только функции своей роли.

«Обновить отчёт» и «Обновить статистику» повторно читают сохранённые данные.
Они показывают подтверждение и время формирования отчёта в часовом поясе
Белграда. Время последнего сбора и последней проверки источника показано
отдельно. Сбор и отправка сообщений выполняются фоновыми заданиями; чтение
отчёта их не запускает. «Проверка базы» показывает диагностику, без очистки.

Синяя кнопка «Меню» рядом с полем ввода — стандартный список команд Telegram.
Команды `/start` и `/menu` открывают главное пользовательское меню. Список
команд в Telegram и кнопки внутри сообщения — разные элементы интерфейса.
