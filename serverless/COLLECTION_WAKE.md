# Резервный запуск сбора из бота

Механизм подготовлен, но **по умолчанию выключен**. Обычная публикация не включает
его, не создаёт ключей и не меняет существующие секреты.

При открытии «Найти вакансии», если успешного сбора не было час, бот может послать
GitHub один `workflow_dispatch` для `catch-up.yml` на `main`. Пользователь продолжает
видеть обычный поиск. Владелец получает в «Сборе вакансий» кнопку «Запросить сбор
сейчас»: она допускает запрос после 30 минут без успешного сбора. В публичном меню
новых кнопок нет. Модераторы и администраторы доступ к этой функции не получают.

Один общий SQLite-лимит допускает запрос раз в 15 минут и до 12 запросов за
скользящие 24 часа. Он действует при параллельных обновлениях и перезапусках.
Действующая аренда сборщика запрещает запрос; просроченная аренда не мешает
восстановлению. `catch-up.py` перед работой заново проверяет свежесть, активность
и аренду. Пауза бота запрещает запуск. Очередь GitHub и аренда коллектора защищают
от параллельных workers. Этот workflow не запускает рекламу.

Перед POST сохраняется неподтверждённая попытка. Таймаут не вызывает немедленного
повтора. HTTP 204 подтверждает только принятие запроса GitHub, **не сбор вакансий**.
Для 429 учитывается `Retry-After`; отказ в доступе останавливает запросы до явной
перенастройки. Ответы GitHub и исключения сети не выводятся в сообщения или логи.

## Одноразовая настройка после отдельного согласования

1. Создать отдельный fine-grained GitHub token для **единственного** репозитория
   `AngryVirus/serbia-jobs-bot`: repository permission **Actions: Read and write**.
   Доступ к содержимому, настройкам, секретам и другим репозиториям не нужен.
   Выбрать ограниченный срок действия; истечение потребует замены этого ключа.
   GitHub не позволяет сузить Actions write до одного конкретного workflow.
2. Через GitHub Settings → Secrets and variables → Actions добавить новый
   repository secret **`SJC_GITHUB_WAKE_TOKEN`**. Значение не отправлять в чат.
   `TGCLOUD_PROBE_TOKEN` и остальные существующие секреты не менять.
3. После успешной публикации этого кода запустить вручную workflow
   **Configure bot collection wake**, ветка `main`, `enabled=true`.
   Секрет передаётся через окружение только шагу настройки и через stdin
   существующему Cloud bridge. В код, аргументы команд и отчёты он не попадает.
4. Владелец видит состояние подключения в «Сборе вакансий». Проверка настройки
   сама по себе не отправляет запрос GitHub и не начинает сбор.

Ключ хранится в приватной SQLite Telegram Serverless. Публичные обработчики
не возвращают конфигурацию; изменение доступно только доверенному owner CLI.
В выгружаемые отчёты и пользовательские данные ключ не входит. Полная резервная
копия содержит эту настройку только внутри существующего зашифрованного артефакта;
обладатель доступа владельца к базе/расшифрованному backup имеет доступ и к ключу.

Отключение: тот же workflow с `enabled=false` удаляет ключ из runtime-конфигурации.
Уже принятый GitHub запрос этим не отменяется. Отзыв ключа в GitHub — отдельное
действие, которое не выполняется автоматически. Старые зашифрованные backup
удаляются по существующему семидневному сроку хранения.

## Ограничения

Это резерв к расписанию GitHub. Без обращений к боту новых запросов не возникает;
при недоступности самого Actions запуск также не гарантирован. Нужное для этого
подключение ChatGPT GitHub не является постоянным доступом Telegram-бота и не
копируется в него. Для полностью независимого регулярного запуска нужен отдельный
планировщик. Существующие проверки успешного сбора и владельческое предупреждение
через два часа сохраняются.

Пользователь видит нейтральное «Последнее обновление — N ч назад» при возрасте
базы от двух часов до суток. После суток появляется заметное предупреждение.
Если успешный сбор никогда не был подтверждён, предупреждение остаётся сразу.
