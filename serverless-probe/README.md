# Проверка Telegram Serverless на @SerbiaJobsBot

**Проверено на платформе 15 октября 2026:** 3 вакансии сохранены, 3 уведомления
отправлены владельцу, повторный импорт дал 0 новых сообщений, webhook не изменился.
Первая проба выполнена напрямую из среды Codex. Затем владелец добавил секрет,
и [ручной запуск GitHub Actions](https://github.com/AngryVirus/serbia-jobs-bot/actions/runs/38755871089)
успешно проверил сбор, импорт, отсутствие дублей и неизменность webhook.
Автоматического расписания и полной миграции приложения пока нет.

Это ограниченная проба, а не готовая миграция. Проверяем цепочку:
Python-сборщик → `tgcloud run` → встроенная SQLite → до трёх сообщений
только в личный чат **@AngryVirus** → повтор без дублирования.

Рабочий Python-бот и Supabase продолжают работать. Здесь нет обработчиков
`handlers/`, команды `push`, `migrate` или `webhook sync` не выполняются.
CLI запускает локальные модули на платформе без их публикации. До и после
пробы сравниваются текущий webhook и список типов обновлений; полный URL
webhook не выводится в лог, поскольку он может содержать секретный путь.

## Запуск с iPhone

1. В @BotFather → **@SerbiaJobsBot → Serverless → CLI Access** скопируйте
   **Access token** вида `app123:…`. Это отдельный токен, не Bot API token.
   Если Serverless ещё выключен, включение нужно для доступа; документация
   не описывает влияние самого переключателя на прежний webhook. После
   включения убедитесь, что обычный `/start` по-прежнему работает. Наш скрипт
   сам этот переключатель и webhook не меняет.
2. В [секретах GitHub Actions](https://github.com/AngryVirus/serbia-jobs-bot/settings/secrets/actions)
   нажмите **New repository secret**. Имя — **TGCLOUD_PROBE_TOKEN**,
   значение — CLI Access token. Токен не нужно отправлять в чат, добавлять
   в файл проекта или вводить в поля запуска workflow.
3. Найдите свой числовой **chat_id** в Supabase → Table Editor → **sj_users**.
   В личном чате он совпадает с `user_id`; `@AngryVirus` вместо числа не подходит.
   Скрипт дополнительно проверит через Telegram, что этот чат принадлежит
   именно `@AngryVirus`, и что токен относится к `@SerbiaJobsBot`.
4. Откройте [Actions → Test Telegram Serverless](https://github.com/AngryVirus/serbia-jobs-bot/actions/workflows/serverless-probe.yml)
   → **Run workflow** → ветка `main` → поле **chat_id** → **Run workflow**.
5. Дождитесь зелёного результата и проверьте личный чат с ботом. Ожидаются
   1–3 карточки с заголовком **«Проверка Telegram Serverless»**.
   В конце лога: `Cloud probe passed: … stored, … sent, 0 repeated; webhook unchanged`.
   Артефакт **serverless-probe-report** содержит результаты проверок.

Запуск только ручной, расписания нет. Это позволяет сначала проверить,
годится ли документированный тестовый `run` для будущего регулярного импорта.
Сбор ограничен каналами `@rabotavserbii` и `@radim_serbia`; используются
существующие Python-адаптеры с robots.txt, паузами и ограничением страниц.
Если подходящих реальных вакансий нет, проба останавливается, а не подменяет их
выдуманными. Все источники основного бота продолжают работать по-прежнему.

## Что проверяется

- Проверка `api.getMe` и `api.getChat` до создания таблиц/отправки.
- Создание двух новых таблиц **sj_probe_jobs** и **sj_probe_deliveries** через
  документированные raw SQL вызовы `db.run`. Здесь нет изменений схемы
  действующего приложения. В Serverless таблицы могут отображаться как
  `undocumented`, так как схема этой пробы не публикуется.
- Сохранение одной вакансии за вызов; чтение записи обратно перед отправкой.
- Проверка сохранённых записей в отдельном вызове платформы.
- Повторный импорт без новых сообщений; уникальная пара чат/вакансия
  предотвращает параллельную повторную отправку.
- Пауза 1,1 секунды между вызовами отправки, без зависимости от таймеров V8.
- В карточку добавляется Maps, только если в реальной вакансии распознан адрес.
  Отсутствие таких адресов в выборке не является ошибкой проверки.

Пример ограничений: после сетевого обрыва Telegram мог уже принять сообщение.
Такая доставка помечается `uncertain` (либо остаётся `sending` при остановке
вызова). Автоматической повторной отправки нет, проверка завершится ошибкой.
Это не гарантия exactly-once. Не удаляйте отметки до проверки чата.
Новые вакансии в последующих ручных запусках могут дать ещё до трёх сообщений;
уже отправленные ссылки повторно не отправляются.

`endpoints/probe` не публикуется и запускается владельцем через CLI.
Он дополнительно отвергает обычный контекст Mini App/Telegram Update.
Токен даёт административный доступ к Serverless-проекту, поэтому workflow
передаёт его только на шагах проверки конфигурации и облачного запуска.

## Локальная проверка

Node.js 22.13+ (для настоящей SQLite в тестах) и Python 3.11+:

```bash
cd serverless-probe
npm ci --ignore-scripts --no-audit --no-fund
npm test
cd ..
python3 -m unittest discover -s tests -p test_serverless_probe.py
python3 serverless-probe/export_jobs.py
```

После настройки `TGCLOUD_TOKEN` и `PROBE_CHAT_ID` через защищённое окружение:

```bash
python3 serverless-probe/run_probe.py
python3 serverless-probe/run_probe.py --status-only
```

Последняя команда только читает состояние вакансий из сохранённого локального
`payload.json`; ничего не отправляет. Файлы payload/report, `.tgcloud/` и
`node_modules/` исключены из Git. Секреты и рабочие пользовательские данные
не включаются в артефакты.

## Практические границы

Локальные тесты используют настоящую SQLite и подмену Telegram API. Отдельный
живой запуск подтвердил raw DDL, сохранение между вызовами и отправку трёх
реальных сообщений. Максимальные лимиты времени и нагрузки не измерялись.
Никакой автоматической миграции пользователей, фильтров или вакансий
из Supabase этот прототип не выполняет. Результат удачной пробы ещё не
подтверждает пригодность платформы для всех 98 источников и массовой рассылки.
