## Фильтр «Наличие ВНЖ»

- **161 тест прошёл**, без пропусков. Новые сценарии проверяют явные требования на русском, английском и сербском, отрицания, отдельное требование разрешения на работу, неизвестные/противоречивые условия, помощь с оформлением и обязанности кадровика.
- Один выбор «Да / Нет / Не важно» применяется к поиску и уведомлениям. Проверены повторные нажатия, переключение, сочетание с другими фильтрами, скрытые и истёкшие вакансии, сброс без очистки скрытых вакансий, объяснение пустой выдачи и единственная кнопка поиска на общем экране.
- Сценарий с реальным SQLite и SupabaseStore с имитацией PostgREST подтверждает сохранение выбора после пересоздания бота, отдельные настройки двух пользователей и совместимость со старыми настройками без нового поля. Новый SQL и столбцы вакансий не нужны: поле хранится в существующем JSON настроек, требование извлекается из исходного текста.
- На локальной сохранённой выборке 384 объявлений распознано одно явное требование ВНЖ (ovdejobs, «Менеджер документооборота»), ни одного явного отсутствия требования; 383 объявления остались без определённого условия. Упоминания помощи с ВНЖ и миграционных обязанностей кадровика не дали ложных совпадений. Это локальная выборка, не проверка действующей базы Supabase.
- Разбор этой выборки занял 19 мс впервые и 0,49 мс при повторе из ограниченного кэша публичных текстов. Новых сетевых запросов нет. Это время локального разбора, не скорость кнопки в Telegram; прежние ограничения Render/Supabase сохраняются.
- Автоматический разбор покрывает распространённые явные формулировки; он не заменяет оригинал объявления. При отсутствии понятного условия варианты «Да» и «Нет» исключают вакансию, «Не важно» сохраняет её. Проверка запуска версии 2.4.0 выполняется после публикации отдельно.

## Предыдущая проверка версии 2.2.1

## Отклик кнопок

- Пользователь подтвердил задержку на каждой кнопке подряд. Во время диагностики три запроса к уже работающему `/health` версии 2.2.0 заняли 0,149–0,162 секунды. Это замер HTTP готовности из среды разработки, не полного пути Telegram → Render → Supabase.
- Прослеживание полного webhook через SupabaseStore с имитацией транспорта показало: меню — 9 запросов к базе, изменение языка — 11. До подтверждения кнопки выполнялись пять запросов, до обновления сообщения — семь и девять соответственно.
- После исправления: меню — 5 запросов, выбор языка — 6; до обновления сообщения — 3 и 4. Подтверждение кнопки выполняется до обращений к базе. Пользовательские настройки читаются при одном upsert без поля settings, а RPC возвращает уже сохранённый результат. Снимок используется только внутри текущего обработчика и очищается при выходе; уведомления продолжают перечитывать действующие настройки.
- **143 теста прошли**, без пропусков. Четыре новых сценария проверяют бюджет запросов и раннее подтверждение, изоляцию пользователей и актуальность между нажатиями, повтор после неудачной записи с сохранением остальных настроек, просроченное подтверждение Telegram и защиту от повторного переключения.
- Настоящий PostgreSQL 16 дополнительно подтвердил, что upsert только user_id/chat_id/updated_at сохраняет существующие настройки, а новый пользователь получает стандартное пустое JSON-поле. Остальные проверки ролей, атомарных обновлений, аренды, webhook и удаления также прошли. Новый SQL для рабочей базы не требуется.
- Уменьшение числа последовательных запросов подтверждено. Фактическое время нажатия в пользовательском Telegram пока не измерено; бесплатный Render всё ещё может засыпать после простоя.

## Что этим не подтверждается

Рабочий Render в начале задачи обслуживал прежнюю версию (`/health` без номера). Подготовленная новая версия не становится работающей от одной проверки локального кода.

Для проверки обновлённого production нужны применение SQL к действующей Supabase, публикация кода в используемую Render ветку, deploy и фактическое взаимодействие двух пользователей в Telegram. Адрес существующей базы известен, серверный ключ в этой среде на момент проверки отсутствовал. Значения секретов не извлекались из Render и не запрашивались в переписку.

Бесплатный сервер засыпает; GitHub schedule допускает задержки/пропуски. Доставка ровно в выбранную минуту не обещается. Авария между успешной внешней отправкой Telegram и записью истории может привести к редкому повтору; штатные пересечения задач и повторные webhook защищены арендами и постоянной историей.

Источник `ok` подтверждает получение ограниченной выборки в конкретном проходе, а не постоянную доступность/полноту. У Halo текущая проверенная выборка истекла, Careerjet ограничивает доступ, Sale-me вернул 404, Lako требует неподтверждённого API, HelloWorld требует разрешения.
