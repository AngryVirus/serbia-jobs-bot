# Проверка версии 2.1.1 — 14 октября 2026 года

## Пустая выдача и навигация фильтров

- **133 теста прошли**: восемь новых проверяют объяснение пустой выдачи, реальные количества при снятии одного ограничения, сохранение настроек, исключение скрытых/истёкших/иностранных объявлений из подсказок, несколько одновременно ограничивающих условий и отсутствие повторных кнопок поиска в отдельных фильтрах.
- В сохранённой проверочной выборке из 384 записей: Белград — 272, Белград + русский — 9, Белград + русский + сегодня — 0. Для последнего сочетания диагностика предлагает снять языковой фильтр (8) или свежесть (9). Это локальная выборка прежнего сбора, не просмотр действующей Supabase.
- Неизвестные язык, формат или дата не превращаются в доказанное совпадение. Условия пользователя сохраняются до его собственного изменения.
- Точная комбинация фильтров из пользовательского сообщения пока не получена; проверка конкретного случая остаётся открытой. Это обновление упрощает навигацию и объясняет пустую выдачу, а не утверждает, что в рабочей базе обязательно есть подходящие вакансии.

## Обновление интерфейса и личных фильтров

- **125 тестов прошли**, без пропусков: прежние проверки и 22 новых сценария. Проверены ИЛИ внутри нескольких городов/языков/форматов/периодов и И между группами, совместимость одиночных настроек, исключительность «любого», галочки и сохранение выбора.
- Проверены компактные/развёрнутые карточки, HTML-экранирование и лимит Telegram с длинными emoji-полями, отказ от ответственности и предупреждение о возможных ошибках при `/start`, пометка тестового режима в меню, актуальные фильтры и состояние уведомлений в главном меню.
- Проверены скрытие для одного пользователя, сохранение после повторного сбора и перезапуска, исключение из уведомлений, восстановление, сохранение истории доставки, пагинация скрытых, переход к следующей странице без пропуска вакансий после скрытия и удаление отсутствующей вакансии из списка. Сброс фильтров сохраняет скрытые, `/delete_me` удаляет их.
- Проверены повторные webhook в двух обработчиках, явные добавление/удаление выбранного пункта, устаревшие кнопки и сериализация уведомлений с изменением пользовательских настроек в другом процессе.
- Новый сценарий прошёл через реализацию `SupabaseStore` с имитацией PostgREST. Дополнительно настоящий PostgreSQL 16 проверил сохранение массивов выбранных значений и скрытых ID, восстановление и изоляцию пользователей через существующий `sj_patch_settings`. Изменения SQL для версии 2.1 не потребовались.
- Источники не изменялись; результаты живых проходов версии 2.0 ниже относятся к тем прежним проверкам, а не к повторному сбору в этом обновлении.

## Подтверждённый запуск предыдущей версии

Версия 2.0 была объединена в `main` (7bfeb00), успешно развёрнута на Render за 7 минут 29 секунд и проверена через публичный `/health` с `version: "2.0.0"`. Telegram подтвердил четыре новые команды и webhook с четырьмя соединениями. Успешный запуск 2.1 проверяется отдельно после её развёртывания.

Внешний GitHub Actions сбор пока требует настройки приватных `COLLECT_URL` и `COLLECT_SECRET`: проверочный запуск 38570889008 получил оба значения пустыми. Внутренний сбор сервера включён; завершение живого production-сбора в рамках этой проверки не инспектировалось.

## Предыдущие проверки версии 2.0

- `python3 -m unittest discover -s tests -v`: **103 выполненных тестов, все прошли**, без пропусков. Включены сохранённые регрессионные тесты; тесты старых пользовательских действий источников/избранного обновлены на проверку их отключения с сохранением старых данных.
- Реальные проверки кода: изоляция двух пользователей, перезапуск, сохранение ввода, комбинированные фильтры, неизвестные/будущие даты, все периоды свежести и границы DST, неизвестные языки, верхняя зарплата и периоды, истечение, страна, пагинация, правильные ссылки помощи и карточек, уведомления/отписка/удаление, повторные webhook в двух экземплярах, одновременные уведомления, миграция старой SQLite, независимая обработка медленного пользователя.
- Полный тестовый путь `JobPosting → parser → SQLite upsert → фильтры → карточка → уведомление → повтор после перезапуска` с проверкой ссылок и истории.
- Настоящий HTTP-сервер на локальном сокете: запуск `serve()`, старт сборщика, GET `/health` с `ok=true, version=2.0.0`; Telegram в этом тесте заменён имитацией, внешняя регистрация webhook не выполнялась.
- `python3 tools/validate_postgres.py` с pgserver 0.1.4 / PostgreSQL 16: SQL применён дважды, сохранение прежних настроек и истории, атомарные JSON-патчи, конкурентная аренда сборщика (победитель один), постоянный webhook claim, триггер неизменной даты первой публикации, доступ только service_role, удаление личных данных с сохранением общих вакансий. Все проверки прошли.
- Повторный живой проход: 379 полученных записей, пять новых ссылок; в SQLite 384 уникальных пары source/url, дубликатов нет.
- Компиляция всех рабочих модулей на Python 3.12.14 прошла.
- Живой сбор: первый проход **379** действующих записей из семи источников. Разбор и сохранение выполнены реальным кодом, без демонстрационных вакансий. Доступ/ограничения всех двенадцати источников проверены отдельно: `SOURCE_NOTES.md`.
- Официальные бесплатные тарифы Render, Supabase и GitHub Actions проверены; ссылки и ограничения приведены в `START_WITH_IPHONE.md`.

## Что этим не подтверждается

Рабочий Render в начале задачи обслуживал прежнюю версию (`/health` без номера). Подготовленная новая версия не становится работающей от одной проверки локального кода.

Для проверки обновлённого production нужны применение SQL к действующей Supabase, публикация кода в используемую Render ветку, deploy и фактическое взаимодействие двух пользователей в Telegram. Адрес существующей базы известен, серверный ключ в этой среде на момент проверки отсутствовал. Значения секретов не извлекались из Render и не запрашивались в переписку.

Бесплатный сервер засыпает; GitHub schedule допускает задержки/пропуски. Доставка ровно в выбранную минуту не обещается. Авария между успешной внешней отправкой Telegram и записью истории может привести к редкому повтору; штатные пересечения задач и повторные webhook защищены арендами и постоянной историей.

Источник `ok` подтверждает получение ограниченной выборки в конкретном проходе, а не постоянную доступность/полноту. У Halo текущая проверенная выборка истекла, Careerjet ограничивает доступ, Sale-me вернул 404, Lako требует неподтверждённого API, HelloWorld требует разрешения.
